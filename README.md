# RunLocal

A practical hub for open source AI. Curated models, the tools to run them,
hands-on install guides, and editorial coverage of the ecosystem.

Built with Next.js 14 (App Router), TypeScript and Tailwind CSS.

## Quick start

```bash
# install dependencies
npm install

# run the dev server
npm run dev

# build for production
npm run build
npm run start
```

The dev server runs on `http://localhost:3000`.

## Project structure

```
runlocal/
  app/                  # Next.js App Router pages
    page.tsx            # Home
    models/             # Model directory
    tools/              # Tool catalog
    guides/             # Install guides (Ollama, llama.cpp, LM Studio)
    blog/               # Editorial posts
    layout.tsx          # Root layout, metadata, header/footer
    globals.css         # Tailwind + prose styles
  components/           # Header, Footer, ModelCard, ToolCard, TrendingSection

  data/                 # Auto-generated: trending.json snapshot
  scripts/              # sync-trending.ts (run via tsx)
  .github/workflows/    # GitHub Action that refreshes trending weekly
  public/               # Static assets
  .env.example          # Environment variable template
  tailwind.config.ts
  next.config.mjs
  tsconfig.json
```

## Editorial principles

- License notes are written in plain English. Before deploying anything
  commercially, read the actual license text.
- Numbers and benchmark claims are attributed. When they come from vendor
  marketing, the post says so.
- No affiliate links on tool or model pages.
- &ldquo;Last reviewed&rdquo; dates are visible. The open weights field moves
  fast enough that anything older than three months should be re-read before
  citing.

## Adding content

Models, tools, guides and posts are static TypeScript files under `lib/`. Each
entry has a `slug` that becomes part of the URL on the corresponding directory
page. Long-form guides and posts live under `app/guides/<slug>/page.tsx` and
`app/blog/<slug>/page.tsx` respectively.

When adding a new model, fill in all fields in `lib/models.ts`. License notes
should be specific (MIT, Apache 2.0, Llama Community License, etc.) rather
than generic (&ldquo;open&rdquo;).

When adding a new guide, include the OS coverage, level, reading time, and
last-updated month in `lib/guides.ts`, then create the corresponding page
under `app/guides/<slug>/page.tsx`.

## Trending models pipeline

The home page and the bottom of `/models` show a "Trending on Hugging Face"
section. The data is generated by a GitHub Action that runs weekly, scores
HF text-generation models by a weighted mix of downloads, likes and recency,
and commits the resulting `data/trending.json` snapshot back to the repo.
Vercel sees the commit and redeploys.

### How the pieces connect

- `lib/hf-core.ts` is the pure logic (types, scoring, normalisation,
  filtering). No Next.js dependencies, so it works inside both the runtime
  fallback and the standalone script.
- `scripts/sync-trending.ts` is the standalone Node script. It fetches the
  HF API, applies `scoreAndPick`, writes `data/trending.json`, and logs a
  diff against the previous snapshot (added/removed entries) for the GitHub
  Action log.
- `.github/workflows/sync-trending.yml` is the workflow. It runs every
  Monday at 06:00 UTC (and on `workflow_dispatch` for manual triggers),
  executes the script with `npm run sync:trending`, and commits the
  snapshot if it changed. The push triggers a Vercel redeploy.
- `lib/hf-static.ts` reads the committed snapshot at request time. If the
  file is missing or empty, it falls back to a live HF fetch with a one-day
  ISR cache.
- `components/TrendingSection.tsx` is a server component that awaits the
  reader and renders the cards. The header shows the snapshot date.

### Configuration

One optional environment variable, defined in `.env.example`:

- `HF_API_TOKEN` (optional). A read-only Hugging Face token, used only to
  bump the API rate limit. Public model metadata works without it.

For the GitHub Action to use it, add a repository secret named
`HF_API_TOKEN` under Settings → Secrets and variables → Actions. The
workflow reads it automatically.

### Running locally

```bash
# generate or refresh the snapshot
npm run sync:trending

# the script writes data/trending.json — inspect the diff with git
git diff data/trending.json
```

The dev server reads `data/trending.json` on render. If the file does not
exist yet, the page falls through to a live HF fetch.

### Manually triggering the Action

In GitHub: **Actions → Sync Hugging Face trending models → Run workflow**.
Useful when a new model release drops mid-week and you want it to appear
on the site before Monday.

### Tuning the scoring

Edit `SCORE_WEIGHTS` in `lib/hf-core.ts`. The default favours signal
(downloads + likes) over freshness, which suits a publication that wants
to surface "what people actually use" rather than "what shipped today."
Push `recency` to 0.4 or 0.5 if you want bleeding-edge releases to
dominate. The change applies on the next sync run.

To filter more aggressively, tighten the thresholds in `isWorthShowing`
inside `lib/hf-core.ts`, or expand `SURFACE_TAG_PREFIXES` to surface the
tags that matter for your audience.

## Deployment

The site is a standard Next.js application with no external services. It
deploys cleanly to Vercel, Netlify, Cloudflare Pages, AWS Amplify or any
container host.

### Vercel

```bash
npx vercel
```

Follow the prompts. Set the build command to `next build` (the default) and
the output directory to `.next` (the default).

### Netlify

Use the official `@netlify/plugin-nextjs` runtime. No further configuration
needed.

### Static export

If the content stays fully static (it currently is), you can run a static
export:

```bash
# adjust next.config.mjs:
# export default { output: "export" }

npm run build
# the static site lands in ./out
```
